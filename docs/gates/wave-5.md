## 1 · The two §4/§2 decisions the kickoff demanded

**Keychain: `WhenUnlocked` stands.** The kickoff's own usage analysis ("minutes to hours, not seconds") survived scrutiny: the drain runs at launch, foregrounding, connectivity return, sign-in, fresh capture, and manual retry, plus the ~30-second `beginBackgroundTask` grant after backgrounding. No code path reads the token while the device is locked, so widening accessibility would have loosened security for nothing. A drain overtaken by the lock fails the keychain read as a *stated, retryable* condition ("Uploads are paused: …") and the next foreground - by definition unlocked - finishes the job. Full argument and rejected alternatives (`AfterFirstUnlock`, `BGTaskScheduler`, background `URLSession`) in `DECISIONS.md`.

**Strict concurrency: on, as `complete` checking in Swift 5 mode.** The kickoff asked for an evaluation given two waves of reviewer-found interleaves. Turning the setting on surfaced ~30 diagnostics in the wave-4 codebase, fixed structurally in an afternoon: `KeptAPI`/`HTTPTransport`/`SessionTokenStore`/`ReceiptTextRecognizer` became Sendable protocols, `APIClient` became a genuinely Sendable all-`let` class (its settable rejection callback became a main-actor relay box), Vision's non-Sendable observations stopped crossing task boundaries, and the JSON date decoding moved to Sendable `FormatStyle` values. The one escape hatch: six cached `Regex` statics are `nonisolated(unsafe)` with the immutability argument stated inline (the stdlib doesn't mark `Regex` Sendable; every current call site is MainActor anyway, so the annotation is defensive). Full Swift 6 language mode was rejected for this wave - the data-race checking is the part with defect evidence behind it, and the zero-warnings discipline makes the diagnostics blocking without the remaining annotation ceremony. **Verdict on the kickoff's hypothesis: correct.** The reviewer still found the wave's worst defect in concurrency (§5) - but it was a *logic* interleave (ownership across suspension points), which no type system flags; the memory-race class the checker does catch produced zero findings for the first time in three waves.

## 5 · Self-review against the anti-pattern list

The read-only reviewer pass ran with the §10 rubric plus this kickoff's watch items (concurrency, error-masking-in-retry) and returned **20 findings: 1 high, 7 medium, 12 low** - the most substantive reviewer haul of any wave, on the wave that most invited it. It also verified sound: the single-flight drain, the step machine across every kill boundary it could construct, the store's atomicity claim, both blocked-item actions' re-find-after-await discipline, and the backoff handshake. The catalog, by category:

- **Concurrency/isolation (high, fixed) - the wave's worst, and the §2 prediction fulfilled:** ownership was checked once per item, before its steps. A drain suspended inside a multi-second upload or create while user A signs out and user B signs in would finish A's item under B's session - creating A's receipt in B's account (constraint 4's worst case) and deleting A's queued copy. Fixed: ownership is re-checked before every step, and the presigned object key - issued for whoever the session names *now* - is only persisted after re-confirming the session still matches the item's owner, so a switch mid-step abandons cleanly and the item resumes intact when its owner returns. Regression-tested by parking the drain on a gated call and switching accounts mid-flight. **Honest residual:** the token is re-read inside APIClient microseconds after the check; a full sign-out-plus-different-sign-in cannot humanly land in that gap, but pinning the token per request is the systematic close - queued for the security review.
- **Error-masking in retry logic (medium-high, fixed) - the kickoff's named watch item, found anyway, three times.** (1) The drain's own token read was a `try?`: a keychain failure ended the pass *silently*, items frozen at "Waiting to upload" with no message, no backoff, no retry - in the same file whose doc-comment claimed "nothing is swallowed". Now a stated queue-level condition with backoff, and one `currentUserId()` derivation with one error policy replaces three divergent ones. (2) A persist failure inside the OCR catch *replaced* the OCR error and, worse, kept the attempt count at zero in memory - making the retry cap unreachable and the item an infinite head-blocker on a persistently failing disk. Now memory-first counting with best-effort persistence, argued at the site. (3) A failing `finishItem` cleanup left a receipt reappearing every launch with no explanation; now stated.
- **Misclassification (medium, fixed):** OCR failures - never queue-wide - stopped the whole pass, so one unreadable page stalled an entire backlog for its backoff cycles. A new `deferItem` outcome sets aside only the troubled item and the pass keeps moving; tested.
- **Wrong-outcome honesty (medium, fixed):** `duplicate_image` was treated as "saved" no matter which call produced it; a hypothetical 409 from the upload-url endpoint would have deleted a receipt that was never created. The 409-is-saved ruling now lives at the create call site alone.
- **Silent deletion (medium, fixed - and it reversed a DECISIONS claim):** my first draft swept commit-less item directories at load as "aborted enqueues already reported failed." The reviewer pointed out `add()` cleans up its own failures, so the only survivors of that shape are kills *between the two writes* - saves the person was never told failed - and my own DECISIONS entry claimed discard was "the only deletion path." Now counted and kept; the entry is corrected.
- **Load resilience (medium, fixed):** a transient disk error at launch made the queue invisible for the whole run (`start()` loaded exactly once). The load now rides every drain trigger until it succeeds.
- **Tests written to pass (medium, two fixed):** the base64-padding test asserted `nil` for its padded cases - which passes with the padding logic *deleted*; it now varies payload length via a filler claim and demands the same correct answer at every remainder. The failed-add test asserted emptiness that held whether or not the cleanup ran; it now checks the directory is gone, and actually fails the write it claims to (image path occupied by a directory).
- **Interleave-adjacent (low-medium, fixed):** sequence numbers were computed before an await and applied after it (two overlapping enqueues could share one; now claimed synchronously); sign-out never reached the outbox (now `onSignedOut` → retries dropped, display cleared - and a signed-out user's own items no longer render as "another account's", which the old derivation implied); the test double's `update` resurrected removed items where production would throw (now strict).
- **UI (low, fixed):** the discard dialog moved from a vanishing-prone `Section` anchor to the `List`; per-receipt list reloads during a batch drain (eighty reloads under the reader's thumb) are debounced to one; the outbox row's date now goes through `ReceiptFormat` like every other date.
- **Accepted, with reasoning recorded:** unreadable/uncommitted records are counted and stated but not yet *actionable* (no per-item discard for them; files stay on disk for recovery - a genuine v1 gap, listed in §6); the `nonisolated(unsafe)` Regex statics (argued inline; all call sites MainActor today); `isDraining` as a test-only hook on a shipping type; the defensive discarded-mid-step guard in `advance` (unreachable through today's UI, kept as structure against tomorrow's).

**Weakest code, named:** (1) still **the drain's failure routing** (`classify` and the switch that consumes it) - materially better than the draft the reviewer shredded, but its correctness rests on every error *type* reaching the right arm, and that mapping is convention, not construction; a new error type introduced by a future wave lands in `default` silently. If wave 6+ touches it, consider making steps return typed outcomes instead of thrown erasure. (2) **The Home outbox UI** - it has zero unit tests (view-layer), had one reviewer finding, and no human eye has seen it render. (3) `rebuildEntries` - correct now, but it recomputes global presentation on every mutation and its signed-out/keychain-failed cases encode policy that lives nowhere else.

6. **Stuck items and manual retry.** Wifi on, but stop the server (`Ctrl-C`). Capture one receipt. **Pass:** it queues, then shows "Will retry" with a message. Restart the server. Without waiting out the backoff, tap **Retry now**. **Pass:** it uploads immediately.
7. **Kill mid-upload (the §3 kill test, live).** Airplane ON, capture one, airplane OFF, and force-quit as fast as you can once "Uploading" shows (racing the upload; if it wins and the receipt lands, just note that - it proves the happy path was too fast to interrupt, which is not a failure). 8. **The pocket case (keychain decision, live).** Capture one receipt with signal and **immediately lock the phone**. Wait a minute. ## 11 · Device re-test (the owner, 2026-08-06): the real defect was assembly, and the evidence came first

The re-test prefilled HST as **17.84 - the total** - the third wrong value from one receipt, which was the owner's tell that no pairing *rule* was at fault: the tax block was not being read structurally. Per his instruction the diagnosis came from evidence, not a model: he queued the scan via **"Later"** (incidentally the outbox's first real device run - enqueue, upload, pending create, Home badge, all clean end to end), the exact uploaded bytes came back off storage, and `ios/Tools/vision-dump.swift` produced the real observations.

**What the geometry showed:** the amount column measured a near-constant **0.013 above** its labels against a **0.022 row pitch** - one coherent receipt-wide skew (camera angle/paper curl), also present milder and inverted (-0.008) on the wave-4 Noodle House dump. At 60% of pitch, every tax-block amount's *nearest* label was genuinely the wrong one: the wave-4 band rule assembled "GST: $2.05" and "HST: $17.84" with `$ 0.00` and `Total:` orphaned - exactly what the stored `ocr_raw_text` showed. Step 1's 0.00 and the re-test's 17.84 were the same single misread; no threshold, nearest-center, or matching variant fixes wrong-nearest.

**The fix:** the assembler estimates the receipt-wide skew (median of each amount-column fragment's delta to its nearest other-column neighbour; zero under 3 samples) and removes it *for grouping only* - emitted rows keep measured geometry. On the real dump this flips all three tax-block pairings to correct and preserves every other row; on Noodle House it tightens every pairing without changing any. The dump is now the fixture, verbatim, asserting HST 2.05 - and the two real fixtures carry opposite skew signs. **The total heuristic re-check** the owner ordered: it survived even the broken assembly (largest-across-total-lines plus this receipt's redundant contiguous `TOTAL: $ 17.84`); its residual exposure and the full-pitch-skew limit are recorded in `DECISIONS.md`, floored as always by constraint 2's human check. Suites: iOS 169 green, server 150, zero warnings; fixed build reinstalled on the device.

**Also banked from this exchange:** §9 step 2 ("Later" queues pending, uploads, badge appears) and the §8 pairing check's upload half are effectively verified; the queued receipt now pending server-side is real data for the accuracy table once confirmed - correct its HST to 2.05 through the badge queue and `parse-accuracy` records the wave's whole story.

## 12 · Airplane-mode run (the owner, 2026-08-06): a store defect, diagnosed evidence-first

The run reported one correct new list row plus "2 saved receipts could not be read" - and per the owner's instruction the diagnosis came entirely from the device state before any code moved. What the evidence showed: the "airplane" capture had actually reached the server (Wi-Fi stays available under airplane mode - the 19:30:19 confirmed row was the tell, so the offline test is still to run, Wi-Fi explicitly off), the new row was genuinely server-backed, and the phone held **three** outbox directories - every item ever enqueued - each with a perfectly decodable `item.json` at `uploaded` and a matching server row. Nothing was lost and nothing was unreadable.

**Root cause, reproduced before fixing:** both `fileExists` checks in `FileOutboxStore` used `URL.path()`, which percent-encodes by default - production lives under "Application Support", so every check asked about `Application%20Support` and got `false`. Remove's idempotency guard therefore reported success without removing (cleanup has never once run on device), and loadAll misfiled every healthy item as "no commit record → could not be read". The count accounted exactly: two leftovers at the last relaunch, the third added by the run itself. **The masking casualty:** items invisible to loadAll never re-entered the queue, so their retried creates never ran - the 409 self-heal, built precisely for replayed uploads, could not reach the very items it existed for.

**Fixed:** `path(percentEncoded: false)` at all five call sites (two production, three in tests), and the store suite's temp directory now carries a deliberate space - the production-shaped path. Falsification verified both ways: with the bug reverted, all 8 store tests fail; restored, 169 iOS green, zero warnings. **Why the suite had been blind:** the test path had no space - the third instance in three waves of a test environment diverging from production in exactly the load-bearing dimension (fabricated Vision geometry; `.env.local` never loaded by the real entry point; now this), recorded as framework §9.3 candidate rule 5 with the strongest evidence of any candidate there.

**Watch on next launch:** the three leftover directories should load as normal items, drain, land on 409, and clean themselves up - the recovery path's first real run, now actually reachable.

## 13 · Offline diagnostic (the owner, 2026-08-06): the transport was lying, not the app

The owner's pre-test check - both radios off, pull to refresh - produced no error and a current-looking empty list, and his framing named the stakes: a person can pull to refresh, see stale data, and believe it is current. The server keeps no request log, so the verdict came from the phone: its URL cache database held the post-wipe `{"receipts":[],"nextCursor":null,"pendingCount":0}` verbatim, and CFNetwork - given no cache directive by the API - had heuristically cached it and served it offline as a fresh 200. **The app's error handling was checked in the same pass and is correct**: a real network failure drops the rows and shows the failure view with reason and Retry, and an empty list does not suppress it. The masking lived a layer below; the app was lied to along with the user. (Same mechanism also served stale detail responses carrying expired presigned image URLs, and a stale pending badge.)

**Fixed both sides, tested both sides:** the API transport now runs a cache-free session (`urlCache = nil` plus `.reloadIgnoringLocalCacheData` - either suffices; both set so neither is load-bearing), and every server response carries `Cache-Control: no-store` from app-wide middleware, so the contract is stated at the source for every future client. The iOS test asserts the transport's *configuration* - CFNetwork's cache behaviour being unreachable from a simulator test, the configuration is the behaviour - and the server tests assert the header on a 200 and a 401. That makes this the **fourth instance of framework §9.3 candidate rule 5**, with the sub-lesson recorded in `DECISIONS.md` per the owner: an unconfigured default in the layer beneath is still a decision, and masking there defeats correct error handling above it. Suites: iOS 170 green, server 152 green, zero warnings.
