# Consolidated security review - August 2026

2026-08-06.
The §10B security review, both passes at once: pass 1 (after wave 1) was never run, so its scope merges with pass 2 (before wave 6) here.
This is the last checkpoint before wave 6 puts the app in front of the second user and before an unlisted App Store link exists that anyone holding it can install.

**Suites after this session:** server 157 green (was 152; five tests added), `tsc --noEmit` clean, iOS 170 green with zero warnings (untouched this session).
**Guardrail 7:** `npm run dev` run from a cleared environment (`env -i`), `.env.local` loaded by the real entrypoint, "Kept API listening on port 3000", and one real `GET /api/me` answering `{"error":{"code":"unauthorized",...}}` with `Cache-Control: no-store`.

## The threat model this review ranks against

Three users, an unlisted App Store link, no public discovery, and - the fact that governs everything below - **no deployed server**.
Unlisted is not private: anyone holding the link installs the app, and in-app authentication plus per-user isolation are the only things protecting the data.
So a finding that exposes data to an unauthenticated stranger with the link outranks one requiring a hostile authenticated user, which in turn outranks one requiring physical possession of a device.

**On issuer and audience.**
The kickoff asks for these, and the session token carries neither.
I am recording this as checked-and-deliberate rather than as a finding: `iss` and `aud` exist to stop a token minted for one party or purpose being replayed at another, and this secret signs exactly one kind of token for exactly one verifier.
There is no second issuer to be confused with and no second audience to cross into, so the claims would assert something already true by construction.
They become worth adding the moment a second token type shares the secret - a download token, a web-session token with a different lifetime - and that is the trigger to revisit, not distribution.
The Apple identity token, which genuinely does cross a trust boundary, has both checked (`src/auth/appleVerifier.ts:50-51`).

**On the dependency audit.**
Six moderate advisories, and the dev-only ones are worth separating from the one that reaches production.
Five are dev-only: `drizzle-kit` pulls a bundled `esbuild` through `@esbuild-kit/*`, and the advisory concerns esbuild's development server, which nothing here runs.
The sixth reaches the runtime tree - `exceljs` depends on `uuid@8.3.2`, and GHSA-w5hq-g745-h8pq is a missing buffer-bounds check in uuid v3/v5/v6 when the caller supplies a buffer.
I verified rather than inherited the prior waves' claim that it is unreachable: `exceljs` imports uuid in exactly one file and calls only `uuidv4()`, twice, with no arguments (`node_modules/exceljs/lib/xlsx/xform/sheet/cf-ext/cf-rule-ext-xform.js:1`, `:43`, `:77`).
The vulnerable code path takes a caller-provided buffer and is never entered.
Both fixes are `isSemVerMajor` downgrades - `drizzle-kit` to 0.18.1, `exceljs` to 3.4.0 - so neither is worth taking for an unreachable path.

## 2 · Findings, ranked by exploitability under the real threat model

### 1. Wave 6 has no server to point at, and the app ships its development networking posture - BLOCKER

There is no deployed API.
`ServerConfig.defaultBaseURL` is `http://localhost:3000` (`ios/Kept/Config/ServerConfig.swift:23`), and the only route to any other address is the in-app server-settings sheet.
The `Info.plist` at `ios/Kept/Info.plist` is used by **both** the Debug and Release configurations - verified at `Kept.xcodeproj/project.pbxproj:277-280` and `:300-303`, where `GENERATE_INFOPLIST_FILE = NO` and `INFOPLIST_FILE = Kept/Info.plist` appear identically in each.
So `NSAllowsLocalNetworking` and `NSLocalNetworkUsageDescription` ship to TestFlight and to the App Store.

**Exploitability.** By itself this exposes nothing: a stranger with the unlisted link installs an app that reaches no server.
It matters because of what it forces next.
If the interim answer is to point the app at a plain-HTTP host on a local network, then the ATS exception is exactly what permits it, and the session bearer token plus every receipt field crosses that network in cleartext to anything listening on it.
That is the one path in this review by which an unauthenticated party on the same network reads another person's tax records.

**Recommended fix.** Deploy the API over HTTPS, make that address the built-in default for Release, and drop both keys from the shipping plist - keeping them, if wanted, in a Debug-only plist.
Then assert the shipped configuration in a test, per framework §9.3 rule 5, since no simulator test can observe ATS.
**Left for a decision:** where the API is deployed and whether the settings sheet survives into production are product calls, not review calls.

### 2. Outbox files hold receipt images and confirmed financial figures at the iOS default protection class - MODERATE

`FileOutboxStore` writes `image.jpg` and `item.json` per queued receipt under `Library/Application Support/Outbox/` with `options: .atomic` and nothing else (`ios/Kept/Outbox/OutboxStore.swift:111-116`, `:128-133`, `:161`).
A search of all of `ios/` for `FileProtection`, `NSFileProtection`, `protectionKey`, `setResourceValues`, and `isExcludedFromBackup` returns zero hits, so these files inherit `NSFileProtectionCompleteUntilFirstUserAuthentication`.
`item.json` carries the capturing user's id, the image digest, the full raw OCR text, and - for a capture confirmed offline - vendor, tax number, every amount, payment method, and notes (`ios/Kept/Outbox/OutboxItem.swift:32`, `:42`, `:66`, `:74-86`), all in plaintext beside the JPEG.

**Exploitability.** Requires physical possession of the device after its first unlock, or an unencrypted backup.
Under a three-user threat model that is the least likely of anything in this review - but it is also the only finding where the data at risk is the receipt images and confirmed tax figures themselves.

**Recommended fix.** `.completeFileProtection` on both writes plus `FileAttributeKey.protectionKey` on the directory creation.
**Left for a decision, deliberately.** This is consistent with the existing posture on paper - the keychain is already `WhenUnlocked`, so the drain cannot run while locked anyway - but it changes runtime behaviour on the `beginBackgroundTask` tail, which is the one drain path that can outlive a lock, and which the wave-5 gate closed under the owner's call without running it (the "pocket case", gate report §15).
Changing file protection would convert that path from "uploads during the grant" to "fails the read and retries on next foreground".
That is a defensible trade and probably the right one, but it is a behaviour change to a device-verified path, so it is a ruling rather than a cleanup.

### 3. No rate limiting anywhere - SPEC REQUIREMENT UNMET, low priority under this threat model

§10B names rate limiting on the auth and upload-url endpoints.
There is none: no limiter, no middleware, no dependency, confirmed by reading `src/app.ts` and grepping `src/`.

**Exploitability under the real threat model, honestly: low.**
`POST /api/auth/apple` is not brute-forceable, because the credential it accepts is an identity token that must carry a valid Apple RS256 signature over the right audience - a stranger with the link cannot guess one.
`POST /api/receipts/upload-url` requires an established session, so only the three real users reach it.
What is left is request volume - cost and availability - against a server that does not yet exist.

**Recommended fix, and why I did not build it.** The limiter's shape depends entirely on the deployment: what identifies a client (a socket address, or a forwarded header - and trusting a forwarded header is itself a security decision that depends on what sits in front of the app), and whether counters live in one process or must be shared.
None of that is decidable before there is a deployment.
Building an in-memory limiter now would encode guesses about a topology that does not exist, which is the kind of decorative control this project has already caught once (the wave-3 presigned content type).
Recommend it lands with the deployment, and note that if the API ends up behind Cloudflare, the edge is the better place for it than the app.

### 4. Object-key validation admitted path traversal out of the user's prefix - FIXED THIS SESSION

`POST /api/receipts` accepted any client-supplied `image.objectKey` beginning `{userId}/`.
That test passes a key such as `{userIdA}/../{userIdB}/2026/03/theirs.jpg`, which starts with A's prefix but names B's namespace once path segments resolve, and which the detail route would then presign a download for.

**What I proved, in both directions.**
The API did accept such a key: reverting the fix makes the new regression test fail with a 201.
It did not, however, leak anything today.
I probed five traversal spellings against the real MinIO container, and none returned the victim's bytes - the AWS SDK collapses dot segments when building the URL while signing the uncollapsed key, so three variants died on `SignatureDoesNotMatch` and two on `NoSuchKey`.

So this was latent, not live.
I fixed it anyway, because the thing standing between a prefix check and a cross-user read was normalization behaviour in the layer beneath - which is precisely the trust that produced the wave-5 CFNetwork cache diagnostic and the wave-5 `URL.path()` encoding defect, and R2's behaviour here is untested since no R2 credentials exist.

**The fix.** `isIssuedObjectKey` in `src/routes/receipts.ts` matches the whole key against the exact shape the upload-url route issues - `{userId}/yyyy/mm/{uuid}.{ext}` - with the extension list read from the same map the issuing route uses, so the two cannot drift.
The issuing route now asserts its own output against the same predicate, so an issued key the create route would refuse is a loud server error rather than a client-visible mystery.

### 5. An unhandled server error prints the failing row, including notes and amounts - LATENT

`renderError` logs `console.error("Unhandled error:", error)` (`src/http/errors.ts:42`).
I reproduced what that actually emits: a Postgres constraint violation arrives with `detail: 'Failing row contains (...)'`, and Node prints it in full.
The reproduction put a vendor name and a private note into the log line, alongside the user id and every amount, plus the SQL text.

**Exploitability.** Low, and I want to be precise about why rather than reassuring.
I could not construct an API request that reaches an unhandled database error: every text column is `text` with no length ceiling to violate, and zod validates before every write, so the paths I can reach return clean 400s.
This fires on an unexpected database condition, not on a crafted request, and today the log is a terminal on the owner's Mac.
It becomes real when §10B's error monitor lands and these lines start leaving the machine.

**Recommended fix.** Log `error.message` and the error's constructor name rather than the object, or strip `detail`/`where`/`query` from database errors before logging.
**Left for a decision:** it trades diagnostic power for confidentiality, and at three users the diagnostic power is currently worth more - that is the owner's call, and the right moment to make it is when the error monitor is chosen.

### 6. The §10B export lifecycle rule cannot be written against the current key layout - DEPLOYMENT DEFECT, not a hole

Export zips land at `{userId}/exports/{jobId}/Receipts-{label}.zip` (`src/export/generateExport.ts:168`), and §10B requires "a 30-day lifecycle expiry on the exports prefix (`{userId}/exports/...`)" while receipt images stay under no lifecycle rule at all.
S3 and R2 lifecycle rules match a **literal** prefix.
`{userId}` varies per user, so there is no single prefix that selects every user's exports without also selecting their receipt images - the rule as the spec writes it is not expressible.

The options are one rule per user (three today, and it grows silently as a thing someone must remember at each new sign-up), object tags applied at upload, or moving exports to `exports/{userId}/{jobId}/...` so one literal prefix covers them all.
**Left for a decision.** The third is cleanest and is a one-line key change plus a note that pre-existing zips under the old layout keep their old prefix, but it is a storage-layout decision with a deployment consequence, so it is not mine to take unilaterally.

### 7. Orphaned objects have no policy - OPEN QUESTION, inert today

Two sources, both already named in the wave-5 gate report §6.4: an image uploaded whose create never completed, and a presign abandoned when an account switch lands mid-step.
Nothing in the system ever deletes a stored object - `ObjectStorage` has no delete operation - so orphans accumulate without bound.

They are inert: keys are uuid-based and unguessable, they sit under the uploader's own prefix, no endpoint lists them, and no lifecycle rule touches them.
Volume is near-zero.
**Left for a decision.** The honest answer may be "no sweep, ever" - a sweep is a deletion path near tax records, which is the thing §10B is most careful about, and the storage cost of a handful of orphaned JPEGs over six years is negligible.
But it should be a written policy rather than an absence.

### 8. Per-request token pinning - RESIDUAL, carried forward from wave 5

`OutboxController.currentUserId()` re-checks item ownership before each step (`ios/Kept/Outbox/OutboxController.swift:181-184`), and then `APIClient.perform` re-reads the token from the keychain when it builds the request (`ios/Kept/Networking/APIClient.swift:116`).
Between those two reads there is a window in which a sign-out plus a *different* account's sign-in would have to complete.

Not humanly reachable - it requires a full Apple sign-in flow inside a few microseconds.
The systematic close is to pass the token that was checked into the request rather than re-reading it.
**Left for a decision**, because the change lands in the drain's session handling, which the wave-5 reviewer named the weakest code in the wave, and a review is the wrong session to restructure it in.

### 9. No privacy manifest, and no accurate privacy label to file - WAVE 6 PREREQUISITE

No `PrivacyInfo.xcprivacy` exists anywhere in `ios/`.
The app uses `UserDefaults` (`ios/Kept/Config/ServerConfig.swift:79`), which is a required-reason API, so a manifest is needed for App Store submission.

On the label itself: the accurate declaration is that the app collects **financial info** (receipt amounts and tax figures), **user content** (receipt photographs and notes), and **identifiers** (the Apple subject identifier), all linked to identity, all stored on a server the owner operates, none used for tracking.
"Data Not Collected" would be false.
The label cannot be filled in honestly until finding 1 is resolved, because where the data goes is part of what the label declares.

## 3 · What I fixed, and what I deliberately left

**Fixed - one change, plus the tests that hold it:**

- Object-key validation tightened from a prefix test to a whole-string match on the issued shape (finding 4), with the issuing route asserting its own output against the same predicate.
- Regression test: a key that walks out of the session user's prefix is refused. Falsified by reverting the fix, which makes it fail with a 201.
- Test: user A can reach user B's image bytes by no route - not by B's receipt id, not by naming B's key on a receipt of A's own, and B's key appears nowhere in A's list response.
- Test: an unsigned `alg: none` token is refused.
- Test: algorithm confusion is refused, both as an HMAC token signed with RSA public-key material and as a genuinely RS256-signed token. Falsified by removing `algorithms: ["HS256"]`, which makes it fail - and the failure is instructive: without the pin, jose raises a `TypeError` rather than a `JOSEError`, so `verify` rethrows and the request becomes a 500 instead of a clean 401. The pin is load-bearing, not decorative.
- Test: a `tv` claim that is a string, a fraction, null, a boolean, or an object is refused - five well-signed tokens differing only in that claim.
- Test helper `imageFor` now produces keys in the shape the upload-url route issues, since that is the only shape the create route accepts; two hand-written keys in the export tests were routed through it.

**Left for a decision, with the reasoning stated at each finding above:** the deployment and shipping plist (1), the outbox protection class (2), the rate limiter's shape (3), whether to strip database detail from logs (5), the export key layout (6), the orphan policy (7), and token pinning (8).

Nothing was weakened, skipped, or disabled to reach a green suite.

## 4 · What I could not verify, and what it would take

- **Cloudflare R2's behaviour on any of this.** Every storage probe ran against the MinIO container. R2's treatment of dot segments in keys, its lifecycle-rule semantics, and its presign behaviour are untested. Needs R2 credentials, which is deployment work.
- **Whether the ATS exception actually permits what I say it permits on a device.** ATS is unobservable from a simulator unit test. The claim rests on reading the plist and both build configurations; the configuration assertion is the available substitute, and it is not yet written as a test.
- **The keychain accessibility class as runtime behaviour.** Verified as the constant at the call sites; a device test with the phone locked is what would verify the behaviour, and no such test exists.
- **Any reachable trigger for finding 5.** I looked for an API request that produces an unhandled database error and did not find one. Absence of a path I could construct is not proof there is none.
- **The Apple JWKS rotation path.** `createRemoteJWKSet` handles rotation by design and the tests inject a fake verifier, so the real key-fetch and refetch have never run in this project. It runs for the first time against Apple on a real sign-in - which every device wave has done, so it works; the *rotation* branch specifically has not been observed.
- **The wave-5 pocket case**, which bears directly on finding 2 and was closed under the owner's call without being run.

## 5 · Go / no-go on wave 6 distribution

**No-go**, and the reason is not the security of the isolation model.

The core property the unlisted-link threat model depends on is sound.
Every route is authenticated, `user_id` comes only from a verified session token, denials are 404 rather than 403, the session JWT pins its algorithm and carries a revocable version checked against the database on every request, the Apple verifier checks signature, issuer, and audience with no configuration path that could bypass it, presigned URLs are short-lived and bind their method and content type, object keys are unguessable, soft-deleted rows are excluded from every read path rather than most, and nothing in the system deletes a tax record.
The one cross-user hole I found was latent rather than live, and it is closed and tested.

Wave 6 is blocked on unfinished distribution work, not on a breach.
There is no deployed server for the app to talk to; the app would ship pointing at `localhost` with its development networking exception intact; and there is no privacy manifest and no honest privacy label to file - and that last one cannot be written until the first is resolved, because where the data goes is what the label declares.

**The minimum to reach go:**

1. Deploy the API over HTTPS and make it the Release default (finding 1).
2. Remove `NSAllowsLocalNetworking` and `NSLocalNetworkUsageDescription` from the shipping plist, and assert the shipped configuration in a test (finding 1).
3. Add `PrivacyInfo.xcprivacy` and file a privacy label naming financial info, user content, and identifiers, linked to identity, not used for tracking (finding 9).
4. Rule on the outbox protection class (finding 2) - it is the only finding whose subject matter is the receipt data itself, and the ruling is cheap even if the answer is "leave it".

Findings 3, 5, 6, 7, and 8 do not block distribution under this threat model, but 3 and 6 should land with the deployment rather than after it, since both are decisions the deployment itself forces.
