# Adversarial audit of the August 2026 security review

2026-08-06, later the same day.
Under audit: `docs/security/review-2026-08.md` and the two commits that carry it, `00a84f4` (object-key matching) and `a67a6ba` (request body limit).
The posture was to falsify, not to confirm.

**Headline.** The review's core claim - that the isolation model holds - survives everything I threw at it, and its two fixes are real rather than decorative.
But the review is **wrong on one finding it dismissed** (finding 5, "no reachable trigger"), **incomplete on the mechanism of that leak**, and **narrower than it states on two others**.
I found one new defect that is both a reachable information leak and an availability-shaped bug, fixed it, and fixed two smaller things the review's own fixes introduced or left.

**Suites:** server 169 green (was 161; eight added), `tsc --noEmit` clean.
**Guardrail 7:** `npm run dev` from a cleared environment (`env -i`), `.env.local` loaded by the real entrypoint, "Kept API listening on port 3000", one real `GET /api/me` answering 401 with `Cache-Control: no-store`, and both fixes re-verified against that running process rather than only against the test harness.

**A note on the kickoff itself.** Its §5.2 states that `bodyLimit` was mounted *after* the `Cache-Control` middleware and asks me to confirm a 413 still carries `no-store`.
The ordering was the other way round, and the 413 did **not** carry the header.
The premise was inverted and the conclusion flipped with it - recorded because an audit brief is an artifact like any other (framework guardrail 6).

### 4.1 - `user_id` derivation

Enumerated myself, not sampled.
Twelve handlers across four files: `auth.ts` (1), `receipts.ts` (6), `exports.ts` (3), `me.ts` (2).
Every authenticated handler takes identity from `c.get("userId")`, which is set only at `sessionAuth.ts:49` from the verified token's `sub`.
No handler reads a user id from a path parameter (the only path parameter anywhere is `:id`), a query key, a body field, or a header.
Every request schema is a zod `strictObject`, so a smuggled key is a 400 rather than something ignored - confirmed live on both create and update.

One narrow observation, not a finding: `session.verify` checks `typeof payload.sub === "string"` but not that it is a UUID, so a malformed `sub` would reach Postgres as a query parameter and raise an unhandled error.
Unreachable without the signing secret, so nobody can trigger it - noted only because validating it is one line and would keep another 500 out of the log path.

### 4.2 - Auth-middleware bypass

Probed differently from the review, as instructed.
Every protected-route request answered 401 (the guard ran) or 404 (no such route); never 200, never a handler.

Notable individual results: absolute-form `GET http://localhost:3000/api/receipts` routed and returned 401, so the guard ran on it.
`/api/receipts/../me` and `/api/foo/../receipts` both 401.
Overlong UTF-8 (`%c0%af`, `%e0%80%af`), `%2e%2e`, `..;/`, `;` parameters, `%2f`, `%09` and `%u0072` all 404 - Hono does not decode them into a matching route.
`X-HTTP-Method-Override` and its two variants changed nothing.
All ten `Authorization` variants - lowercase `bearer`, uppercase `BEARER`, duplicate headers, tab before the scheme, doubled spaces, empty value - returned 401; the prefix check at `sessionAuth.ts:28` is case-sensitive and there is no path around it.
CL.TE and TE.TE smuggling shapes were both rejected by Node's parser with 400 before Hono saw them.

### 4.3 - The object-key predicate, and the question the fix does not answer

**The predicate itself held against all 21 attacks**, as user A with a legitimately issued key as the control.
Rejected: uppercase UUID, uppercase user-id prefix, B's whole key, dot-segment walk, `%2e%2e`, double-encoded `%252e%252e`, backslash walk, a suffix walk out of a valid key, Arabic-Indic digits, fullwidth digits, a UUID-shaped non-hex string, `.jpeg`, `.xjpg`, `.pdf.jpg`, an embedded space, an embedded newline, a leading slash, and B's prefix with A's suffix.
The two `\d{2}` groups accept `99` as a month and `0000` as a year, both of which create successfully - but the key still sits under the caller's own prefix with an unguessable UUID, so this grants nothing and I am recording it as laxity rather than a finding.

**What the fix does not do is re-validate on read**, and this is where the claim narrows.
`isIssuedObjectKey` is a write-time gate only.
`GET /api/receipts/:id` presigns whatever `object_key` the row holds (`receipts.ts:258`) with no check that the key still belongs to the row's owner.
I proved this: I created a receipt for A legitimately, updated the image row's `object_key` to B's key directly in the database, and requested the detail as A.
The response was 200 and carried **a presigned download URL naming B's namespace**.

`npm run db:claim` is exactly a mutation of this shape.
It updates `receipts.user_id` and `receipt_images.user_id` (`claim.ts:48-56`) and touches `object_key` in no statement, so every claimed receipt afterwards carries a key under the *synthetic seed user's* prefix while owned by the real user.
Today that is inert - seed rows have no bytes in storage, and no API route can move a receipt between users - so it needs database access to reach, which puts it below a hostile authenticated user in the ranking.
It is worth stating because "we issued every key in the system" is the sentence the fix exists to make enforceable, and it is currently enforceable at write time only.

### 4.4 - MinIO traversal: the review's reassurance is spelling-dependent

I planted a victim object and probed 13 spellings, with a control proving the probe can observe a leak.

The review's five dot-segment spellings reproduce exactly: `SignatureDoesNotMatch` (403) for the raw ones, `NoSuchKey` (404) for the encoded ones, plus `XMinioInvalidObjectName` and `XMinioInvalidResourceName` (400) for two I added.
So far, upheld.

**But a leading slash leaks.**
`/victim-user/2026/08/secret-receipt.jpg` and `//victim-user/...` both returned **200 with the victim's bytes**.
MinIO normalizes the leading slash away and serves the object; the signature matches because the SDK signs and requests the same normalized form.

This does not leak through the API - the whole-string match rejects a leading slash, because `startsWith(userId + "/")` fails first, and I confirmed that live.
Its significance is what it says about the review's reasoning.
The review concluded the hole was "latent, not live" *because the storage layer collapses dot segments*, and rested on that behaviour.
That behaviour is not a property of the storage layer; it is a property of the particular spellings tested.
A different spelling class normalizes the other way and resolves.
So the whole-string match is doing more work than the review credited it with, and the fix's own comment - that this is "the layer beneath deciding an isolation question" - now has evidence behind it rather than analogy.

**On Cloudflare R2, plainly: this tells us nothing.**
Every result above is MinIO's key-normalization behaviour. R2 is a different implementation with no credentials in this project and no test ever run against it. Given that one normalization class already goes the other way on MinIO, assuming R2 matches either result would be unfounded.

### 4.5 - Re-deriving the body limit from the schemas

Derived independently, without reusing the review's arithmetic.
zod's `.max()` counts UTF-16 code units and JSON can spend six bytes per code unit (`\uXXXX`, and surrogate pairs keep the same 6-bytes-per-unit ratio), so six is the correct multiplier.

Worst-case create body: `ocrRawText` 600 000 + `notes` 30 000 + `vendor` 1 200 + `category` 1 200 + `paymentMethod` 600 + `vendorTaxNumber` 300 + `ocrSuggestions.vendor` 1 200 + `ocrSuggestions.vendorTaxNumber` 300 + `image.objectKey` 3 000 + `sha256` 64 + seven money fields + three dates + currency + status + structural punctuation and keys.
**Total ≈ 623 KiB**, against a 1 MiB cap.
Update is a subset and smaller; `updateMe` and both export shapes are trivial.
My number agrees with the review's ~640 KB, so **the claim is upheld and there is no latent outage**.

**The derivation, however, does not hold as stated.**
The review and its DECISIONS entry both say "every body is JSON the schemas already bound."
`appleSignInSchema.identityToken` is `z.string().min(1)` with **no maximum** (`schemas.ts:64`).
On the one route reachable without a session, the 1 MiB cap is not derived from a schema bound - it *is* the only bound.
No practical outage follows, because a real Apple identity token is roughly a kilobyte, but the sentence that justifies the number is inaccurate on exactly the route that matters most.

### 4.6 - Is the body limit real or theatre?

**Real.** This is the claim the kickoff most wanted re-attacked, and it survives.

I read `hono/dist/middleware/body-limit/index.js` rather than assuming: when `transfer-encoding` is present it takes a streaming branch that accumulates chunks and calls `onError` the moment the running total exceeds the cap, so the honest-`Content-Length` fast path is not the only guard.

Measured against the running server, sampling RSS and fds throughout:

- **Chunked, no `Content-Length`, 50 MB × 6 concurrent.** Every connection was reset after sending 2.8-4.0 MB. RSS went 55 → 83 MB and stayed there. Bounded and proportional, not attacker-unbounded. The gap the kickoff suspected is closed.
- **Lying `Content-Length`** (declares 50, sends 5 MB): connection reset, no response, RSS +3 MB. Node's parser delivers only the declared bytes; the remainder is parsed as a pipelined request and fails.
- **Malformed `Content-Length`** (`abc`, `1e9`, `0x100000`, leading space, `100, 100`, `-1`): all 400 from Node's parser before Hono. This matters because `bodyLimit` does `parseInt(...)` and `NaN > maxSize` is false, which would fall through to `next()` - the path is unreachable only because the layer beneath rejects first. Worth knowing it rests there.
- **Slow drip and stalled connections.** 200 connections, then 1 500: fds 22 → 1 522, **RSS flat at 80 MB**, zero connect errors, and legitimate requests still answered in 1-6 ms throughout. I could not degrade service. The consumable resource is file descriptors, not memory, and Node's default `requestTimeout` (300 s) is what eventually reclaims them - a deployment-level concern, not an application defect.

### 4.7 - Soft deletes

Enumerated every query site myself and spot-checked the citations against source.
**Nine read sites** (seven on `receipts`, two on `receipt_images`), not the twelve the review claimed - the review appears to have counted writes alongside reads.
The conclusion is unchanged and correct: **every read excludes soft-deleted rows**, including the export path, the `pendingCount` badge query, and both image lookups.

Two details the review did not surface:

- `parseAccuracyReport.ts:58-60` hand-rolls `eq(userId) + isNull(deletedAt)` instead of using `visibleTo()`. Correct today, and it is the one receipts read that does not use the helper whose stated purpose is that "a handler cannot get one right and the other wrong."
- The image soft-delete at `receipts.ts:377-385` has no `deleted_at IS NULL` guard of its own. It cannot overwrite an older tombstone today only because the receipts update above it returned zero rows and short-circuited first. The guard rests on caller ordering rather than on the statement.

### 4.8 - Retention and the dev scripts

No API path hard-deletes anything: `DELETE /api/receipts/:id` issues two `UPDATE ... SET deleted_at` statements, and `ObjectStorage` (`objectStorage.ts:17-30`) declares exactly four methods with **no delete operation at all**, so no caller can remove a stored object through that boundary.
`s3ObjectStorage.ts` imports no `DeleteObjectCommand`.

**The review was right to treat `db:claim` as harmless and wrong to skip `db:seed`.**
`seed.ts:13-15` issues three unconditional deletes - `receipt_images`, `receipts`, `users`, no WHERE clause - which wipe every row including soft-deleted tombstones held for the six-year retention requirement.
The only thing deciding which database that hits is `process.env.DATABASE_URL` (`seed.ts:6-8`), which falls back to the local dev URL but honours the variable when set.
Wave 4 built exactly this guard for the test path: `assertSeparateTestDatabase` compares host, port and database name and refuses to aim at the dev database, proven by its own unit test.
`db:seed` has no equivalent guard, and it is the more destructive of the two.
Under today's threat model this is not an attack - it is an operator footgun, on the one thing §10B calls non-deferrable.

### 4.9 - The iOS claims

All five upheld; I confirmed the two load-bearing ones against source myself.

- **Keychain:** `kSecAttrAccessibleWhenUnlocked`, defined at `SessionTokenStore.swift:74` and applied on **both** the add path (`:79`) and the update path (`:88`), so the attribute cannot drift on re-save.
- **Token duplication:** exactly one `UserDefaults` key exists in the whole app, `"apiBaseURLOverride"` (`ServerConfig.swift:17`), and the only value written is a validated URL string. The token exists nowhere but the keychain.
- **Logging:** grep for `print(`, `NSLog`, `os_log`, `Logger`, `debugPrint`, `dump(` across `ios/Kept/` returns **zero**. The only hits in the repo are in `ios/Tools/vision-dump.swift`, a standalone script not referenced by the Xcode project.
- **File protection:** zero occurrences of `FileProtection`, `protectionKey`, `completeFileProtection` or `setResourceValues` anywhere in `ios/`. The outbox writes at `OutboxStore.swift:111-116`, `:129-132` and `:161` pass `options: .atomic` and nothing else.
- **ATS ships in Release - confirmed from `project.pbxproj` directly.** `GENERATE_INFOPLIST_FILE = NO` and `INFOPLIST_FILE = Kept/Info.plist` appear identically in the Debug config (lines 278-279) and the Release config (lines 301-302). Those are the only two `INFOPLIST_FILE` lines in the file, there are no `.xcconfig` files and no `INFOPLIST_KEY_*` overrides, and a plist has no conditional compilation. So `NSAllowsLocalNetworking` and the `NSLocalNetworkUsageDescription` string reading "during development builds" both land in a shipped Release bundle.

One correction of emphasis on the review's finding 1: `NSAllowsLocalNetworking` relaxes ATS for local and link-local hosts only, not for arbitrary internet hosts.
The accurate statement is "an ATS exception ships in Release", not "cleartext to any host ships".
It remains a real finding, because `ServerConfig` accepts any `http://` URL with a host and defaults to `http://localhost:3000`, so a Release build will carry bearer-token-authenticated traffic in cleartext to any LAN address entered in the settings sheet.

## 2 · New findings, ranked by exploitability

### N1. An amount above `int4` returns 500 and prints the whole receipt to the log - FIXED THIS SESSION

**This is the finding, and it breaks the review's finding 5.**

Every money column is a Postgres `integer` (`schema.ts:59-66`), maximum 2 147 483 647.
`centsSchema` validated only `Number.isSafeInteger`, which allows up to 2^53.
So `totalCents: 2147483648` passed validation, reached the insert, and failed inside the transaction as an unhandled error.

Measured against the running server: `2147483647` → 201, `2147483648` → **500**, `Number.MAX_SAFE_INTEGER` → 500, `-2147483649` → 500, and the same through `hstCents`, `subtotalCents`, `otherTaxCents` and PATCH.

**What reached the log.** I sent a receipt with realistic content and an overflowing total. `renderError` printed a `DrizzleQueryError` whose `params` array carried, in plaintext:

```
'Dr Smith Psychiatry Clinic', '123456789RT0001', 'medical',
'visa ending 4412', 'PRIVATE: therapy session, do not disclose',
'PATIENT COPY - Dr Smith Psychiatry - session fee', <user uuid>
```

**Two ways the review was wrong about this.**

First, reachability. The review wrote that it "could not construct an API request that reaches an unhandled database error" and ranked the finding low on that basis, reasoning that "every text column is `text` with no length ceiling to violate."
That reasoning looked at the string columns and never looked at the integer ones. The trigger is a plain authenticated request with a large number in it.

Second, the mechanism. The review hunted Postgres's `detail: 'Failing row contains (...)'` field.
In this error `detail` is `undefined`.
The leak comes from **drizzle's own error wrapper**, which attaches `params` - every bound parameter of the statement - and that fires on *any* failed query, not only on the constraint violations that carry a failing row.
A fix targeting `detail` would not have closed it.

**Exploitability: highest of anything new here, though it needs a session.**
It needs no crafted encoding, no race and no privilege - one field of one ordinary request.
It does not cross the isolation boundary: a user can only make the server log *their own* receipt.
But it converts an information-disclosure finding the review parked as unreachable into one reachable at will, and today the log is a terminal on the owner's Mac only because §10B's error monitor has not landed yet.

**The fix.** `centsSchema` now bounds to the int4 range with a stated message, so the failure is a 400 naming the field instead of a 500 (`schemas.ts`).
Verified against the real server after the fix: 400 with `"totalCents: is outside the storable amount range"`, the boundary value 2 147 483 647 still accepted, and **zero unhandled errors and zero PII in the log** for the same request that previously dumped it.
Eight tests, falsified in both directions - removing the bound fails all six rejection tests while the boundary-acceptance test keeps passing, which is what stops a future tightening from refusing a legitimate amount.

**Left for a ruling, deliberately:** `domain/money.ts`'s `cents()` still accepts any safe integer, and `money.test.ts:15-17` explicitly asserts that it accepts `Number.MAX_SAFE_INTEGER`.
So the domain's stated contract and the storage column genuinely disagree.
I fixed the HTTP boundary, because an API that 500s on input it just validated is unambiguously a bug, and left the domain alone, because narrowing it means changing a test that encodes deliberate intent - and the rule is that a failing test is a finding, not something to rewrite in passing.

### N2. A 413 refused before any route carried no `Cache-Control` - FIXED THIS SESSION

`bodyLimit` was mounted at `app.ts:53`, ahead of the cache middleware at `:77`.
Its `onError` returns a response without calling `next()`, so the cache middleware never ran and the 413 went out bare.
Confirmed against the running server: the 401 carried `cache-control: no-store`, the 413 carried nothing.

This is a small consequence of the previous fix rather than a hole - the exposure is an intermediary caching a "too large" answer.
It matters mainly because the app-wide claim in the spec's update log, in DECISIONS and in the middleware's own comment is "every API response", and the existing test asserted only a 200 and a 401, both of which pass through a route.

**The fix.** The cache middleware is now outermost, with the reason stated in place.
One test that requests a 2 MiB body and asserts both the 413 and the header; it fails if the ordering is restored.

### N3. The isolation suite's cross-user download assertion could not fail - FIXED THIS SESSION

The kickoff flagged this and it is correct, though not quite for the stated reason.
In `isolation.test.ts`, "never hands A a download URL for an object B owns" ended with `expect(await ownList.text()).not.toContain(bObjectKey)`.
A owns no receipts at that point, so the list is empty - and independently, the list projection carries no object keys at all (`receiptResponse`, `receipts.ts:403-423`), so the assertion would hold even for a user with receipts and even if isolation were broken.
It passed for two reasons, neither of them isolation.

The test's other two assertions were load-bearing, so the test as a whole could fail - but its headline assertion could not, in freshly written security code, which is the anti-pattern framework §10.2 names.

**The fix.** A now creates its own receipt and the assertion moved to the one response that actually carries presigned URLs - A's own detail - checking that it contains A's key and neither B's key nor B's user id.
Falsified by removing the receipt-id and user-id scoping from the detail route's image query, which makes it fail; restored after.

### N4. `db:seed` can wipe a real database with no guard - REPORTED, not fixed

Covered under 4.8 above.
Not an attack under this threat model, and the fix is a product decision about how the dev scripts should behave, so I have not taken it.
The shape of the answer already exists in `assertSeparateTestDatabase`.

### N5. Presigned image URLs are plain HTTP today - OBSERVATION

The dev configuration points storage at `http://dev-mac.local:9000`, so presigned download URLs the API hands the phone are `http://`.
Receipt image bytes therefore cross the LAN unencrypted.
This is dev-only and not shipped, but it is the same substance as the review's finding 1 and belongs with it when the deployment is decided: the ATS exception, the API base URL, and the storage endpoint are three separate places that each have to become HTTPS.

## 3 · Defects in the two fixes themselves

The kickoff called this the highest-value thing to find. Three, all minor - the fixes are sound in substance.

1. **`a67a6ba` introduced N2**, the missing `Cache-Control` on its own 413. Fixed.
2. **`a67a6ba`'s stated derivation is inaccurate** (4.5): `identityToken` carries no schema maximum, so on the one unauthenticated route the cap is not schema-derived. The number is still correct.
3. **`00a84f4`'s claim is write-time only** (4.3): reads never re-validate a stored key, and `db:claim` produces exactly the state that exposes the gap. Reported, not fixed - rewriting stored keys or adding a read-time check is a storage-layout decision.

Neither fix is theatre.
The body limit genuinely bounds chunked bodies, which was the specific suspicion, and the key predicate genuinely refuses every crafted key I could construct.

## 4 · Does the no-go on wave 6 stand?

**Yes, and its stated reasons are the right ones.**

The three blockers the review names are real and I confirmed the load-bearing one from the project file directly: there is no deployed server, the app would ship pointing at `localhost` with an ATS exception in the Release bundle, and there is no privacy manifest - which cannot honestly be written until the deployment exists, because where the data goes is what the label declares.
Nothing I found displaces them or adds a fourth blocker.

**One re-ranking.** The review's finding 5 should move up.
It ranked it low on "no reachable trigger"; there is one, and the leak is broader than described.
Its trigger is now fixed, so the finding no longer blocks anything - but the underlying decision it parks, whether `renderError` should log a raw error object, is now a decision about a code path a user can reach on purpose rather than a hypothetical.
That changes the weight of the ruling, not the wave-6 verdict, and it should be made when the error monitor is chosen rather than after.

**The review's central security claim survives audit.**
Every route authenticated, `user_id` only from a verified token, denials as 404 rather than 403, the algorithm pinned and the `tv` claim checked against the database on every request, object keys unguessable and now whole-matched, soft deletes excluded from every read path rather than most, and no code path that hard-deletes a tax record.
I attacked all of it and moved none of it.

## 5 · What I could not verify

- **Cloudflare R2, on anything.** Every storage result here is MinIO's. Section 4.4 makes this sharper rather than softer: one normalization class behaves the opposite way from the class the review tested, so R2's behaviour cannot be inferred from either. Needs credentials, which is deployment work.
- **ATS as runtime behaviour on a device.** Unobservable from a simulator. The claim rests on the plist and both build configurations, which I read directly; the configuration assertion is the available substitute and is still not written as a test.
- **Keychain accessibility as runtime behaviour.** Verified as the constant at all three call sites; a device test with the phone locked is what would verify the behaviour.
- **The Apple JWKS rotation branch.** Never executed in this project. Sign-in exercises the fetch; rotation specifically has not been observed.
- **The wave-5 pocket case**, which bears on the outbox file-protection finding and was closed under the owner's call without being run. Unchanged from the review.
- **Whether 1 500 stalled connections is the ceiling.** I stopped there because service was still healthy; the real ceiling is the deployed process's fd limit, which no deployment defines yet.
- **The body limit against a real device.** Unchanged from the review's own note: no create carrying a long `ocrRawText` from real Vision output has passed through the cap. My derivation says a 100 000-character OCR text fits with roughly 400 KiB to spare, and a test now sends a create at the schemas' maximum, but that is arithmetic and a harness, not a phone.

## 6 · What I changed

Three fixes, eight tests, each falsified in both directions:

- **`src/http/schemas.ts`** - money bounded to the storable `int4` range (N1). Six rejection tests across all four money fields and PATCH, plus one asserting the boundary value is still accepted. Removing the bound fails the six; the seventh is what stops the bound being tightened into a real refusal.
- **`src/app.ts`** - the `Cache-Control` middleware moved outermost so it also covers responses no route produced (N2). One test; restoring the old order fails it.
- **`tests/integration/isolation.test.ts`** - the vacuous cross-user assertion rewritten against A's own detail response, where a leak could actually appear (N3). Breaking the detail route's image scoping fails it.

Nothing was weakened, skipped or disabled.
The suite went 161 → 169, all green, `tsc --noEmit` clean.
The dev database was left as found (3 users, 9 receipts); every probe created its own users and deleted them, and `npm test` still resets `kept_test` only, guarded by `assertSeparateTestDatabase`.

**Left for a ruling:** the `cents()` domain contract versus the int4 column (N1), read-time key re-validation and what `db:claim` should do with `object_key` (4.3), a `db:seed` guard (N4), and everything the review already left open - the deployment and shipping plist, the outbox protection class, the rate limiter's shape, whether database `detail` is stripped from logs, the export key layout, the orphan policy, and token pinning.

## 7 · Note on machine state

A stale `npm run dev` from the prior review session (started 20:47) was holding port 3000 - the fourth wave running that this has been found - and was killed before the real entrypoint was started, so every measurement here ran against current code.
This is now frequent enough to be a pattern rather than an incident.
